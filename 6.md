## 3. Test Cases: The Atomic Refund Transaction

* **UI Action:** Click "Refund Order" in Organizer dashboard → Confirm modal
* **API Endpoint:** `POST /api/v1/orders/{id}/refund`
* **Payload:** `{"reason": "Customer requested cancellation due to scheduling conflict"}`

### A. Normal Execution (Happy Path)
| Test ID | Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REF-01** | Execute Full Refund on a paid order (e.g., 2 tickets totaling `10 000.00 KZT`). | 1. Confirmation dialog opens showing amount (`10 000.00 KZT`), ticket count (2), and optional reason input.<br>2. On confirmation, one single DB transaction executes.<br>3. Order row updates to `status = 'refunded'`, `refunded_kzt = total_kzt`.<br>4. UI turns order status pill red (`Refunded`).<br>5. Terminal 2 logs `refund.completed` mock email.<br>6. Analytics and inventory panels refresh automatically. | **HTTP 200 OK**<br>Returns updated order object. |

### B. Database Row-Level Integrity Verification
Run this query directly after executing **REF-01** to ensure full transaction consistency:
```bash
docker compose exec -T db psql -U biletflow -d biletflow -c "
SELECT o.id, o.status, o.total_kzt, o.refunded_kzt, 
       p.status as payment_status, r.status as refund_status, r.is_simulated
FROM orders o
JOIN payments p ON p.order_id = o.id
JOIN refunds r ON r.order_id = o.id
WHERE o.id = '<ORDER_UUID>';"
```

| Table Verified | Column | Expected Value | Purpose |
| :--- | :--- | :--- | :--- |
| `orders` | `status` | `'refunded'` | Order marked terminal state. |
| `orders` | `refunded_kzt` | Identical to `total_kzt` | DB check constraint `orders_refund_not_above_total_chk` satisfied. |
| `payments` | `status` | `'refunded'` | Original payment marked reversed. |
| `refunds` | `status`, `is_simulated` | `'succeeded'`, `true` | Immutable refund ledger row created. |
| `tickets` | `status` | `'refunded'` | Every ticket tied to the order is voided. |
| `audit_logs` | `action` | `'order.refunded'` | Non-deletable audit log entry recorded. |

## 4. Test Cases: Inventory Restocking & Re-Availability

A refund must return inventory so the event does not sell out against tickets that no longer admit anybody.

| Test ID | Scenario | Step-by-Step Verification | Expected Result |
| :--- | :--- | :--- | :--- |
| **RESTOCK-01** | Verify `quantity_sold` decrement and `quantity_refunded` increment. | 1. Note `ticket_types.quantity_sold` before refund (e.g., 10 sold).<br>2. Refund an order containing 2 tickets.<br>3. Inspect `ticket_types` table in DB:<br>`SELECT quantity_sold, quantity_refunded, quantity_total FROM ticket_types WHERE id = '...';` | `quantity_sold` decrements to **8**.<br>`quantity_refunded` increments to **2**.<br>`quantity_sold` always equals count of active (`valid` + `checked_in`) tickets. |
| **RESTOCK-02** | Re-sale on Public Page: Event was sold out (0 remaining). Refund 1 order. | 1. Open public event page `/events/[slug]`.<br>2. Previously sold-out tier now shows `1 remaining`.<br>3. Add ticket to basket and complete a new checkout successfully. | Restocked ticket can be purchased by a new attendee. |
| **RESTOCK-03** | Dashboard Analytics Refresh. | Organizer dashboard statistics re-key immediately: Gross revenue remains tracked, but net demonstration revenue and sold percentages adjust to reflect the refund. | Analytics panel figures update without manual browser reload. |

## 5. Test Cases: Door Scanner Invalidation (Gate Rejection)

Verify that refunding an order physically prevents the ticket holder from entering the venue.

| Test ID | Scenario | Step-by-Step Procedure | Expected Result |
| :--- | :--- | :--- | :--- |
| **GATE-REF-01** | Scan a refunded ticket at the entrance. | 1. Take the QR code (or token string) of a ticket refunded in REF-01.<br>2. Scan it using the mobile scanner app (or type token in manual input). | 1. Mobile app displays **FULL RED SCREEN**.<br>2. Rejection message: *"This ticket is refunded and cannot be used for entry."*<br>3. API returns **HTTP 409 Conflict** (`ticket_not_valid`).<br>4. No row is written to `check_in_records`. |
| **GATE-REF-02** | **Post-Check-in Refund:** Refund an order where the attendee was *already checked in* earlier in the night. | 1. Check in a ticket via Phase 5 (status becomes `checked_in`, `checked_in_at` set).<br>2. Organizer executes refund on that order.<br>3. Verify DB state: `tickets.status = 'refunded'` and `tickets.checked_in_at IS NULL` (satisfying constraint `tickets_checked_in_consistency_chk`).<br>4. Verify history: Prior `check_in_records` row is **retained** (attendance history is not erased).<br>5. Scan the ticket again: Gate rejects it. | Ticket voided; gate refuses repeat entry; historical scan record preserved. |

## 7. Test Cases: Concurrency & Edge Cases

| Test ID | Scenario | Expected Behavior | Expected Error Code / Status |
| :--- | :--- | :--- | :--- |
| **REF-ERR-01** | **Duplicate Refund Click:** Two organizers click "Refund" on the exact same order at the same instant. | Backend opens transaction with `SELECT ... FROM orders WHERE id = $1 FOR UPDATE`. First request locks row and completes refund. Second request sees `status == 'refunded'` and aborts. | First: **200 OK**<br>Second: **409 Conflict** (`order_already_refunded`) |
| **REF-ERR-02** | Attempt to refund an already refunded order via direct API call. | Refused immediately; prevents duplicate accounting entries. | **HTTP 409 Conflict** (`order_already_refunded`) |
| **REF-ERR-03** | **Unauthorized Organizer:** Organizer B (`timur@biletflow.kz`) attempts to refund an order belonging to Organizer A (`dana@biletflow.kz`). | Permission check verifies event ownership against bearer token. | **HTTP 403 Forbidden** (`forbidden`) |
| **REF-ERR-04** | Attendee Self-Refund: Attendee attempts to call `POST /orders/{id}/refund` directly. | Only organizers and platform admins may issue refunds in the MVP. | **HTTP 403 Forbidden** (`forbidden`) |
| **REF-ERR-05** | Attempt to refund an order for an event that is `suspended`. | Platform rules allow refunds on suspended events (organizers or admins can refund attendees if an event is suspended). | **HTTP 200 OK** |

## Phase 6 Sign-Off Checklist
You can consider Refunds & Order Management **PASSED** if:
- [ ] Organizers can view a complete breakdown of orders, buyer names, and ticket statuses.
- [ ] Refunding an order updates the order status to `refunded` and creates a corresponding `refunds` ledger entry.
- [ ] Ticket statuses transition to `refunded`, and any previously set `checked_in_at` timestamp is cleanly cleared.
- [ ] `ticket_types.quantity_sold` decrements and restocked tickets immediately become purchasable again on the public event page.
- [ ] Scanning a refunded ticket at the mobile door scanner produces a full RED rejection screen.
- [ ] Historical attendance logs in `check_in_records` are preserved even if an order is refunded after check-in.
- [ ] Two simultaneous refund requests on the same order cannot double-refund (locked `FOR UPDATE`).
- [ ] Non-organizers cannot issue refunds.
- [ ] A formatted `refund.completed` mock notification is recorded in the outbox and printed to the terminal console.
