# Phase 1: Accounts & Authentication Testing Specification

This specification covers **only** Identity, Authentication, and Account Lifecycle (SRS 4.1, Phase 2, and Phase 12). 

---

## 1. Setup & Environment for the Tester

Before running any test in this phase, initialize the database, the API (which prints mock emails to terminal output), and the Next.js frontend.

### Terminal 1: Database
From repository root:
```bash
make up
# Ensure clean state or demo data:
make seed
```

### Terminal 2: Go Backend API
```bash
make api-run
```
> **Critical Testing Note:** Keep this terminal visible at all times! Because this is an academic MVP with simulated email delivery, verification links and password-reset tokens are logged directly to `stdout` in this terminal window.

### Terminal 3: Web Application
```bash
make web-dev
```
Open your browser at: `http://localhost:3000`

## 2. Test Cases: User Registration

* **UI Route:** `/register`
* **API Endpoint:** `POST /api/v1/auth/register`
* **Payload:** `{"email": "...", "password": "...", "full_name": "..."}`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REG-01** | Fill `email`, `password`, and `full_name` with valid values. | User is created in DB; JWT token is issued and set in `biletflow_token` cookie; user is immediately redirected to `/dashboard` without needing a second login step. | **HTTP 201 Created**<br>`access_token`, `expires_at`, `user` object returned. |
| **REG-02** | Omit `full_name` completely (provide only `email` and `password`). | Backend automatically derives `full_name` from the email local part (e.g., `alibek.k@demo.kz` becomes `"Alibek K"`). Account created successfully. | **HTTP 201 Created**<br>`user.full_name` contains formatted local part. |

### B. Edge Cases
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REG-03** | Register with mixed-case email (e.g., `Dana.Amirova@Example.KZ`). | Email stored and queried via PostgreSQL `citext`. The user is created and can subsequently log in with all-lowercase or all-uppercase. | **HTTP 201 Created** |
| **REG-04** | Password of exactly 72 bytes. | Validated, hashed with bcrypt cost 12, and accepted without truncation. | **HTTP 201 Created** |
| **REG-05** | Very long email address (e.g., 250 characters). | Handled properly within database string constraints. | **HTTP 201 Created** |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **REG-ERR-01** | Duplicate email (e.g., register with existing `dana@biletflow.kz`). | **JSON:** `{"error": {"code": "conflict", "message": "Email already in use."}}`<br>**UI:** Field error or alert banner on email input: *"Email already in use"* (or matching validation copy). | **409 Conflict** |
| **REG-ERR-02** | Duplicate email with differing letter case (e.g., `DANA@BILETFLOW.KZ`). | Treated as duplicate due to `citext` column. | **409 Conflict** (`conflict`) |
| **REG-ERR-03** | Malformed email (e.g., `notanemail`, `@missing.com`, `spaces in@email.com`). | **JSON:** `{"error": {"code": "validation_failed", "fields": {"email": "Invalid email address format."}}}`<br>**UI:** Highlights the email input with red border and message. | **422 Unprocessable Entity** |
| **REG-ERR-04** | Password longer than 72 bytes (Bcrypt truncation protection). | **JSON:** `{"error": {"code": "validation_failed", "fields": {"password": "Password exceeds maximum length of 72 bytes."}}}` | **422 Unprocessable Entity** |
| **REG-ERR-05** | Blank / missing password or empty body `{}`. | **JSON:** `{"error": {"code": "validation_failed", "fields": {"password": "Password is required."}}}` | **422 Unprocessable Entity** |

## 3. Test Cases: Sign-In & Session Management

* **UI Route:** `/login`
* **API Endpoint:** `POST /api/v1/auth/login` and `GET /api/v1/auth/me`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **LOG-01** | Correct email and password (e.g., `dana@biletflow.kz` / `biletflow-demo`). | Authenticates; sets `biletflow_token` cookie; redirects to `/dashboard`. Terminal shows successful login. | **HTTP 200 OK**<br>Body has `access_token`, `expires_at`, `user`. |
| **LOG-02** | Deep link with return param: Visit `/dashboard/events/new` while unauthenticated. | Next.js server proxy bounces user to `/login?next=%2Fdashboard%2Fevents%2Fnew`. After entering valid credentials, user is redirected directly to `/dashboard/events/new` rather than the default `/dashboard`. | **HTTP 307 / 302 Redirect** |
| **LOG-03** | Sign Out: Click "Sign Out" in header. | Cookie `biletflow_token` is cleared; user state is purged from React context; redirected to `/login`. Navigating back via browser history bounces back to `/login`. | Cookie cleared. |

### B. Edge Cases
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **LOG-04** | Email case insensitivity: Enter `DANA@BILETFLOW.KZ` and correct password. | Successfully authenticates without requiring matching case. | **HTTP 200 OK** |
| **LOG-05** | Timing Attack Prevention: Test login with an unregistered email vs. registered email with wrong password. | Both requests must take comparable response time (due to dummy bcrypt hash comparison). | Comparable response latency. |
| **LOG-06** | Cookie tampering: Manually alter one character in the `biletflow_token` cookie using browser DevTools and refresh `/dashboard`. | `proxy.ts` passes request optimistically, but `AuthProvider` calls `GET /auth/me`, gets 401, clears the corrupt cookie, and bounces user to `/login`. | **HTTP 401 Unauthorized** |
| **LOG-07** | Simultaneous Roles: Sign in with `dana@biletflow.kz`. | `GET /auth/me` returns array containing both `organizer` and `attendee` roles. UI recognizes role set without errors. | **HTTP 200 OK** |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **LOG-ERR-01** | Wrong password for existing user. | **JSON:** `{"error": {"code": "invalid_credentials", "message": "Invalid email or password."}}`<br>**UI:** Displays banner: *"Invalid email or password"*. Does not say which part was wrong. | **401 Unauthorized** |
| **LOG-ERR-02** | Non-existent email. | **JSON:** `{"error": {"code": "invalid_credentials", "message": "Invalid email or password."}}`<br>**Note:** Must match `LOG-ERR-01` identically to avoid account enumeration. | **401 Unauthorized** |
| **LOG-ERR-03** | Suspended Account: Suspend an account directly in DB (`UPDATE users SET status = 'suspended' WHERE email = '...'`), then attempt login. | **JSON:** `{"error": {"code": "forbidden", "message": "Account has been suspended."}}` | **403 Forbidden** |
| **LOG-ERR-04** | Pre-existing Token on Suspended Account: Login successfully, then update DB to `suspended`. Try clicking any protected route or trigger `GET /auth/me`. | Server re-reads DB row on auth check. The token is immediately rejected; session is cleared. | **403 Forbidden** or **401 Unauthorized** |

## 4. Test Cases: Password Reset Flow

* **UI Routes:** `/forgot-password`, `/reset-password?token=...`
* **API Endpoints:** 
  * `POST /api/v1/auth/password-reset/request`
  * `POST /api/v1/auth/password-reset`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **RST-01** | Submit valid registered email on `/forgot-password`. | 1. Browser shows generic confirmation message.<br>2. Go API terminal logs: `MOCK EMAIL - Type: account.password_reset` with a raw token/URL.<br>3. Open the reset link in browser (`/reset-password?token=...`).<br>4. Enter new password, confirm it, and submit.<br>5. Password is updated in DB (as a new bcrypt hash).<br>6. Old password no longer works; new password works. | **HTTP 202 Accepted** on request.<br>**HTTP 200 OK** on reset. |

### B. Edge Cases & Security Checks
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **RST-02** | User Enumeration Prevention: Submit `doesnotexist@nowhere.kz` on `/forgot-password`. | Response is **identical** to `RST-01`. No mock email is printed to console, but client UI displays the exact same success message: *"If an account exists with this email, instructions have been sent."* | **HTTP 202 Accepted** |
| **RST-03** | Superseding Tokens: Request password reset 3 times consecutively for the same address. | Terminal prints 3 tokens. Only the **3rd token** should work. The previous 2 must be invalidated by the DB update. | Token 1 & 2 fail; Token 3 succeeds. |
| **RST-04** | Reset does NOT auto-login: Submit a successful password reset. | The response must NOT return a session JWT. User is redirected to `/login` to sign in manually with their new password. | Redirect to `/login`. |
| **RST-05** | Token Hashing Check: Check `user_tokens` table in PostgreSQL. | The plaintext token from the email does NOT appear in the database. Only its SHA-256 hash is stored. | Plaintext token absent from DB. |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **RST-ERR-01** | Re-using an already consumed token. | **JSON:** `{"error": {"code": "invalid_or_expired_token", "message": "Reset token is invalid or has expired."}}`<br>**UI:** Displays error banner indicating the link is no longer valid. | **400 Bad Request** |
| **RST-ERR-02** | Bogus/malformed token (e.g., `/reset-password?token=fake12345`). | **JSON:** `{"error": {"code": "invalid_or_expired_token", "message": "Reset token is invalid or has expired."}}` | **400 Bad Request** |
| **RST-ERR-03** | Expired token: Manually alter `expires_at` in DB (`UPDATE user_tokens SET expires_at = now() - interval '1 hour' WHERE ...`) and try to submit. | **JSON:** `{"error": {"code": "invalid_or_expired_token", "message": "Reset token is invalid or has expired."}}` | **400 Bad Request** |
| **RST-ERR-04** | Client Password Mismatch: Type `password123` in field 1 and `password456` in confirm field on `/reset-password`. | Handled client-side before sending to API. Form blocks submission and indicates passwords do not match. | Blocked in UI. |

* **API Endpoints:** 
  * `POST /api/v1/auth/verify-email/request` (Authenticated)
  * `POST /api/v1/auth/verify-email` (Public)

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **VRF-01** | From an unverified account session, request email verification. | 1. Terminal prints `MOCK EMAIL - Type: account.email_verification`.<br>2. | Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |

## Phase 1 Sign-Off Checklist
You can consider this phase **PASSED** if:
- [ ] Users can register with or without `full_name`.
- [ ] Duplicate emails (including case-variants) return HTTP 409.
- [ ] Valid users can log in, receive a cookie, and navigate protected routes.
- [ ] Account suspension takes effect immediately on the next user action without waiting for token expiration.
- [ ] Passwords over 72 bytes are rejected with a 422 validation error.
- [ ] Resetting password via console link works, uses SHA-256 hashed DB tokens, and rejects stale/consumed tokens.
- [ ] Email enumeration via "Forgot Password" is fully prevented.
