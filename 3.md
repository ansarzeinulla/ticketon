# Phase 3: Attendee Checkout & Inventory Testing Specification

This specification covers **only** the attendee checkout experience, ticket selection, price calculations in KZT, inventory locking, concurrency guards, and order placement (SRS 4.3, 4.4, 4.5, 4.6, 4.14, and Phase 4, Phase 7, Phase 10).

---

## 1. Setup & Environment for the Tester

Treat this as an independent testing phase. Checkout must work completely without being logged in (guest mode), but can also be tested with a logged-in user.

### Terminal 1: Database
```bash
make up
make seed
```

### Terminal 2: Go Backend API
```bash
make api-run
```
> **Keep Terminal 2 in view:** When a checkout completes, the API will output a formatted `order.confirmation` mock email to `stdout`.

### Terminal 3: Web Application
```bash
make web-dev
```

### Test Target
Open a private/incognito browser window at:
`http://localhost:3000/events/almaty-winter-jazz-night` (or any published event slug).

## 5. Test Cases: Concurrency & Overselling Prevention

These tests verify that PostgreSQL row locking (`FOR UPDATE`) and check constraints stop two attendees from buying the same final ticket.

### A. Race Condition Simulation
| Test ID | Scenario | Step-by-Step Test Procedure | Expected Result |
| :--- | :--- | :--- | :--- |
| **CONC-01** | **The Two-Buyer Race for the Last Ticket** | 1. In DB or Organizer Dashboard, set a ticket tier stock to `quantity_total = 1`, `quantity_sold = 0`.<br>2. Open Browser A (Chrome) and Browser B (Firefox) to `/events/[slug]`.<br>3. In both browsers, select the 1 remaining ticket and open the checkout dialog.<br>4. Click "Pay" in Browser A.<br>5. Immediately (within 1 second) click "Pay" in Browser B. | • **Browser A:** Succeeds, redirects to `/orders/[id]`.<br>• **Browser B:** Rejection received from Go API:<br>**HTTP 409 Conflict**<br>`{"error": {"code": "insufficient_inventory", "remaining": 0}}`<br>• **Browser B UI:** Displays banner: *"These tickets sold out while you were choosing. The page has been refreshed."* Calls `router.refresh()` to update live counts. |
| **CONC-02** | Concurrency CLI verification | Run the automated backend race test: `cd api && go test ./internal/api/ -run TestCheckoutDoesNotOversellUnderConcurrency -v` | Fires 30 parallel goroutines at 10 tickets. Exactly 10 succeed, 20 fail with 409; `quantity_sold` in DB equals exactly 10. |

* **UI Component:** `PromoBox` on `/events/[slug]`
* **API Endpoint:** `POST /api/v1/events/{id}/promo/preview`

### A. Normal Cases (Happy Path)
| Test ID | Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **PRM-01** | Apply typed promo code (e.g., `JAZZ20` for 20% off). | Client debounces 250ms, calls `/promo/preview`. Server calculates discount on the applicable tiers using `math/big.Rat`; returns discount in KZT. Order summary displays strikethrough price and updated total. | **HTTP 200 OK**<br>Returns calculated discount. |
| **PRM-02** | Arrive via Campaign URL (`/events/[slug]?c=CMP_...`). | Page parses `?c=` query parameter, auto-fills and validates promo code on arrival. Discount shows immediately. | Promo auto-applied on page load. |

| **PRM-04** | Remove Promo Code: Click "Remove". | Promo code is cleared. Basket reverts to full price. Changing ticket quantities does **not** accidentally re-apply the promo code. | Promo stays removed. |

### B. Error Cases & Edge Conditions
| Test ID | Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **PRM-ERR-01** | Invalid / Non-existent promo code typed. | **JSON:** `{"error": {"code": "promo_not_found", "message": "Promotional code does not exist."}}` | **404 Not Found** |

## Phase 3 Sign-Off Checklist
You can consider Attendee Checkout **PASSED** if:
- [ ] Attendees can check out as guests without registering an account.
- [ ] Free checkouts bypass payment prompts and generate an order + QR ticket instantly.
- [ ] Paid checkouts record simulated payments, update inventory, and create valid tickets in one transaction.
- [ ] Inventory overselling is physically impossible under high concurrency (verified via 409 `insufficient_inventory` and automated race tests).
- [ ] Unactivated paid events block paid sales while keeping free tickets open.
- [ ] Running totals never suffer floating-point roundoff issues (always exact KZT and tiyn).
- [ ] Promo codes correctly re-price on ticket count changes and lock atomically during checkout.
- [ ] Suspended or cancelled events cleanly block checkout with appropriate banners.
- [ ] Completing a checkout logs an `order.confirmation` mock email to the API terminal output.
