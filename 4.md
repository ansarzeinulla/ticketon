# Phase 4: Digital Delivery & Printable PDF Testing Specification

This specification covers **only** digital ticket delivery, the order confirmation capability view, high-DPI QR generation, and print-ready A4 PDF ticket rendering (SRS 4.7, Phase 5, and Phase 12).

---

## 1. Setup & Environment for the Tester

Digital ticket delivery relies on an unguessable capability URL: tickets and PDFs must be accessible without requiring an account (allowing guest buyers to download and print their tickets).

### Terminal 1: Database
```bash
make up
make seed
```

### Terminal 2: Go Backend API
```bash
make api-run
```

### Terminal 3: Web Application
```bash
make web-dev
```

### Test Target
Either:
1. Complete a checkout from Phase 3 to reach `/orders/[id]`, or
2. Use the seeded order ID from `make seed`. Inspect the database to get a test order UUID:
```bash
docker compose exec -T db psql -U biletflow -d biletflow -c "SELECT id FROM orders LIMIT 1;"
```
Open: `http://localhost:3000/orders/<ORDER_UUID>`

## 2. Test Cases: Order Confirmation & Web Ticket Display

* **UI Route:** `/orders/[id]` (Server Component)
* **API Endpoint:** `GET /api/v1/orders/{id}`

### A. Normal Cases (Happy Path)
| Test ID | Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **DEL-01** | Open `/orders/[id]` in an incognito window (unauthenticated guest). | The page renders without requiring sign-in. Displays Order number, event details, total amount paid in KZT, buyer details, and a ticket card for each ticket purchased. | **HTTP 200 OK** |
| **DEL-02** | QR Code Image Rendering on Web (`TicketCard`). | Each ticket displays a crisp, black-and-white QR code. Inspecting the DOM shows a plain `<img>` element pointing to `/api/v1/tickets/{id}/qr.png` (deliberately not using `next/image` to prevent compression artifacts or optimizer caching). | HTML `<img>` tag with direct API `src`. |
| **DEL-03** | Multi-Ticket Orders: View an order with 4 tickets (e.g., 2 General, 2 VIP). | Order page displays 4 distinct ticket cards. Each ticket has its own unique ticket ID, distinct admission token, and separate "Download PDF ticket" link. | 4 unique ticket cards rendered. |

### B. Edge Cases & Security Checks
| Test ID | Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **DEL-04** | QR Token vs Ticket UUID Decoupling. | 1. Note the ticket UUID in the URL (`/tickets/<UUID>`).<br>2. Scan the on-screen QR code with your phone camera.<br>3. Verify the decoded string begins with `TKT_` and is followed by a **different** random UUID.<br>*(The public ticket ID must never double as the admission secret).* | Decoded QR != Ticket ID.<br>QR matches `^TKT_[a-f0-9\-]{36}$`. |
| **DEL-05** | Cache-Control Header Check. | Run: `curl -I http://localhost:8080/api/v1/tickets/<TICKET_ID>/qr.png`<br>Verify `Cache-Control: no-store` is present so browsers/proxies do not cache a ticket that may later be refunded or cancelled. | `Cache-Control: no-store` |

### C. Error Cases
| Test ID | Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **DEL-ERR-01** | Open `/orders/[id]` with a non-existent UUID. | Server Component handles 404 cleanly; renders "Order not found" page. | **404 Not Found** |
| **DEL-ERR-02** | Malformed Order ID in URL (e.g., `/orders/abc-123-not-a-uuid`). | Backend returns `validation_failed`; frontend renders not-found state without crashing. | **400 Bad Request** / **404 Not Found** |

## 3. Test Cases: PDF Generation & Download

* **UI Action:** Click "Download PDF ticket" on `/orders/[id]`
* **API Endpoint:** `GET /api/v1/tickets/{id}/pdf`

```bash
# Direct download test via cURL:
curl -sI http://localhost:8080/api/v1/tickets/<TICKET_ID>/pdf
```

### A. Normal Cases (Happy Path)
| Test ID | Scenario | Expected Behavior | Expected Result |
| :--- | :--- | :--- | :--- |
| **PDF-01** | Click "Download PDF ticket" in browser. | The browser triggers a file download directly (via plain `<a href>` with `Content-Disposition: attachment; filename="..."`), rather than opening a blob in JavaScript. | File downloads as `ticket-<TICKET_SHORT_ID>.pdf`. |
| **PDF-02** | Inspect PDF Geometry & Page Size. | Open the PDF in Acrobat, Preview, or Chrome. Check document properties: Dimensions must be standard **A4 portrait** (`595.28 × 841.89 pt` or `210 × 297 mm`). | Exactly 1 A4 page. |
| **PDF-03** | Mandatory Fields Presence: Review printed fields against SRS 4.7. | Verify the PDF includes:<br>1. Event Title<br>2. Event Date & Time in the **Event's local timezone**<br>3. Venue Name and Venue Address<br>4. Attendee Name<br>5. Ticket Type Name (e.g., "VIP Admission")<br>6. Ticket Identifier & Order Reference<br>7. Assigned Seat (Section, Row, Seat) or "General Admission"<br>8. Clear admission QR code | All 8 fields present and legible. |

### B. Privacy & Security Verifications (Exclusions)
| Test ID | Scenario | Expected Behavior | Expected Result |
| :--- | :--- | :--- | :--- |
| **PDF-04** | Absence of Sensitive Financial Data (SRS 4.7 compliance). | Search PDF content for: Payment card numbers, CVV, billing address, or internal processing identifiers. | **Zero** financial or payment-card details appear on the PDF. |

### C. Localization & Transliteration Checks
| Test ID | Scenario | Expected Behavior | Expected Result |
| :--- | :--- | :--- | :--- |
| **PDF-05** | Cyrillic Event Title & Attendee Name (e.g., `"Концерт в Алматы"`, Attendee: `"Нұрлан Сағындық"`). | Because the PDF engine uses Helvetica cp1252, verify that Cyrillic text is safely **transliterated** (e.g., `"Kontsert v Almaty"`, `"Nurlan Sagyndyk"`) instead of rendering mojibake (`????` or corrupted glyphs). | Text is clean Latin transliteration, no question marks. |
| **PDF-06** | Accented Latin Characters (e.g., `"Café Del Mar"`). | Latin-1 supplement characters render properly without corruption. | Accents display correctly. |

## 4. Test Cases: QR Code Resolution & Scannability

Per SRS 4.7, printable tickets must remain reliably scannable from standard A4 paper, in color or grayscale, and when folded or damaged.

### A. Resolution & Fallback Verification
| Test ID | Scenario | Expected Behavior | Verification Method |
| :--- | :--- | :--- | :--- |
| **SCAN-01** | Visual Backup String. | Below the QR code box on the PDF, the full raw token (e.g., `TKT_4eaea347-...`) is printed in legible monospace text for manual door staff entry. | Text is clearly printed beneath the graphic. |
| **SCAN-02** | Physical Print & Grayscale Scanning. | 1. Print the PDF ticket on a standard office printer (or export to black-and-white 700 px image).<br>2. Open your phone camera or barcode scanner.<br>3. Aim at the paper copy from 30 cm away at a 45-degree angle. | Decodes instantly to the exact `TKT_...` token string. |
| **SCAN-03** | Fold / Crease Tolerance (High Error Correction). | Fold the printed A4 ticket horizontally and vertically across the edge of the QR code (simulating an attendee keeping it in their pocket). Scan it again. | Thanks to ~30% Reed-Solomon error correction, the code scans without error. |

## 5. Automated Backend PDF Verification

To verify that the PDF content streams and QR generation round-trip byte-for-byte at the binary level, run the Go test suite:

```bash
cd api && go test ./internal/ticketpdf/... -v
cd api && go test ./internal/api/ -run TestQRRoundTripsTheExactToken -v
```

### Expected Output:
* `TestQRRoundTripsTheExactToken`: Generates QR, uses `gozxing` library to decode it back, asserts the string matches the PostgreSQL `qr_token` byte-for-byte.
* `TestPDFTicketRendering`: Inflates the compressed PDF content streams, asserts that the text-showing operators contain the expected event name, venue, and transliterated strings.

## Phase 4 Sign-Off Checklist
You can consider Digital Delivery & PDF **PASSED** if:
- [ ] Anyone holding a valid Order ID can view their tickets without logging in.
- [ ] Each ticket card displays a clean QR image served with `Cache-Control: no-store`.
- [ ] The decoded QR token begins with `TKT_` and uses a distinct random UUID, not the ticket's database ID.
- [ ] Clicking "Download PDF" initiates a direct file download (`Content-Disposition: attachment`).
- [ ] PDF document conforms to standard A4 geometry (single page).
- [ ] Event dates and times on the PDF reflect the event's configured timezone, not UTC or browser time.
- [ ] No payment-card or sensitive checkout details appear on the ticket.
- [ ] Cyrillic characters are transliterated rather than output as broken glyphs.
- [ ] The raw token string is printed beneath the QR code as a manual entry fallback.
- [ ] The QR code scans reliably from a grayscale or printed copy.
