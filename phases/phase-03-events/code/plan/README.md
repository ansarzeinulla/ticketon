# BiletFlow — план на семестр (CSCI 361, осень 2026)

Как пятеро доводят проект от пустого репозитория до работающей системы за 13 фаз,
не мешая друг другу.

## Где ваши инструкции

**Не здесь.** Этот файл читают один раз. Каждый день вы открываете свой файл в
папке фазы:

```
phases/phase-05-paid-sales/
    captain.md    ← капитану: открыть фазу, следить, закрыть, поставить тег
    S1.md … S5.md ← каждому своё: ветка, файлы, команды, что двигать в Jira
    code/         ← как проект выглядит к концу этой фазы
```

Внутри готовые команды — копируются и выполняются, думать не надо. Собираются
командой:

```bash
python3 plan/tools/build-phases.py
```

## Шесть правил

1. **Единица работы — фаза, а не неделя.** Фаза длится от полунедели до двух.
2. **Цикл жёсткий:** завести задачи → сделать фазу → закрыть задачи → сразу
   завести задачи следующей. Фазы не перекрываются.
3. **Одна задача = один коммит = одно название.** За фазу человек делает 1–3
   такие задачи.
4. **У каждого файла ровно один владелец** (`ownership.map`). Чужой файл не
   трогает никто — поэтому merge-конфликтов не бывает в принципе.
5. **Коммитим то, что написано сегодня**, а не то, как оно будет выглядеть в конце.
   Файлы рождаются простыми, переписываются, удаляются, переименовываются.
6. **Jira ведётся заранее.** Задача, заведённая после работы, видна по датам.

## Три ветки

| Ветка | Живёт | Кто трогает |
| --- | --- | --- |
| `main` | всегда | **никто напрямую** |
| `phase-05` | одну фазу | все пятеро вливают в неё свои PR |
| `phase-05/aslan-BF-40` | одну задачу | один человек, один коммит |

Ветки задач удаляются сами после слияния (галочка *Automatically delete head
branches*). Ветки фаз остаются навсегда — по ним видно, как рос проект.

## Главное правило коммитов

> **Коммитим то, что написано сегодня, а не то, как оно будет выглядеть в конце.**

Если гнаться за финальным качеством каждой строки, файлы только растут, а `git log -p`
состоит из одних плюсов. Нормальная разработка выглядит иначе: код, написанный в Ф2,
переписывается в Ф10, и строки **удаляются**.

Поэтому не бойтесь писать просто и переделывать потом. `auth/password.go` выходит в
Ф2 с ограничением bcrypt в 72 байта — потому что так пишут, пока не столкнулись с
казахским паролем на 40 букв. В Ф10 это ограничение удаляется. Исходники первых
версий лежат в `file-histories.md`: когда в вашей инструкции стоит пометка
**v1**, берите оттуда.

Три уровня файлов:

| Уровень | Что | Как коммитить |
| --- | --- | --- |
| **A** | ~25 хабовых и переписываемых файлов | v1 руками, позже отдельный коммит переписывает |
| **B** | большинство обычных `.go` / `.tsx` | растут за 2–4 коммита |
| **C** | `package-lock.json`, шрифты, иконки, Postman | одним коммитом целиком |

## Файлы этой папки

| Файл | Что это |
| --- | --- |
| `README.md` | этот файл: правила, роли, календарь |
| `ownership.map` | **источник правды:** правила «файл → владелец» |
| `reports/` | семь двухнедельных отчётов |

Пофазные инструкции в `phases/` и отчёты **генерируются** из `timeline.md`.
Руками их не правят: правят таймлайн и перезапускают генератор. Таймлайн,
`file-histories.md` и `tools/` — локальная оснастка команды, в репозиторий они
не коммитятся (см. `.gitignore`).

| Инструмент | Что делает |
| --- | --- |
| `tools/build-phases.py` | пересобирает `phases/`: снимки кода + все инструкции |
| `tools/gen-reports.py` | пересобирает семь отчётов |
| `tools/check-plan.py` | семь проверок самого плана |
| `tools/stats.py` | сколько кому предстоит сделать: файлы и строки по фазам |
| `tools/diff-phases.py N` | что меняется между Ф(N−1) и ФN |
| `tools/new-phase.sh N` | ветка `phase-NN` + рабочая папка |
| `tools/check-history.sh` | метрики истории: доля правок, удалений, переименований |

## Перед каждым репортом

```bash
python3 plan/tools/check-plan.py      # семь проверок плана
bash plan/tools/check-history.sh      # метрики истории
```

`check-plan.py` проверяет:

| # | Что проверяет | Зачем |
| --- | --- | --- |
| 1 | у каждого файла есть владелец | ничья зона — будущий конфликт |
| 2 | ни один файл не правили два автора | главная проверка непересечения |
| 3 | `timeline.md` не противоречит карте | план не нарушает собственные зоны |
| 4 | каждый файл где-то **создаётся** | иначе в плане дыра: файл есть, а взяться ему неоткуда |
| 5 | ссылки `BF-*` существуют | документы не разъезжаются с планом |
| 6 | смесь операций A/M/D/R | план должен предсказывать живую историю |
| 7 | переходы между фазами возможны | нельзя изменить файл до создания |

Ключевая метрика второго скрипта — **удалённых строк ÷ добавленных ≥ 0.20**.
Поползла вниз — значит фаза спланирована как набор добавлений: найдите файл,
который должен был быть переписан, и перепишите его.
