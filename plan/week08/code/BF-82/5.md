# Phase 5: Event Check-In (Mobile App & Web) Testing Specification

This specification covers **only** gate management, mobile QR ticket scanning, duplicate entry prevention, gate staff delegation, check-in reversal, and manual attendee admission (SRS 4.8, 4.14, Phase 6, Phase 10, and Phase 12).

---

## 1. Setup & Environment for the Tester

Treat this as an independent testing phase. You need the database running with seed data, the backend API running, and the React Native / Expo mobile app.

### Terminal 1: Database
```bash
make up
make seed
```

```bash
make api-run
```

### Terminal 3: Mobile Scanner App (Expo)
From the repository root:
```bash

cd mobile && npm install && npx expo start
```

* Scan the displayed Expo QR code with the **Expo Go** app on your physical iOS or Android test device.

## 3. Test Cases: Mobile QR Scanning & Real-Time Admission

* **UI Action:** Mobile Camera Scanner view & "Enter code by hand" input
* **API Endpoint:** `POST /api/v1/events/{id}/check-in`
* **Payload:** `{"qr_token": "TKT_...", "device_label": "Gate 1 Scanner"}`

### A. Normal Admission (Green Screen)
| Test ID | Scenario | Expected Behavior | Expected Screen / Status |
| :--- | :--- | :--- | :--- |
| **CHK-01** | Scan a valid, unused ticket QR (e.g., `TKT_DEMOSEAT00000000A1` or fresh checkout ticket). | 1. API responds in < 2 seconds.<br>2. Transaction sets `tickets.status = 'checked_in'` and writes row to `check_in_records`.<br>3. Mobile app flashes **FULL GREEN SCREEN**.<br>4. Displays: Attendee Full Name, Ticket Type (e.g., "VIP"), Assigned Seat (if applicable), and live gate count. | **HTTP 200 OK**<br>Full Green Screen |

### B. Duplicate Admission & Fraud Prevention (Red Screen)
| Test ID | Scenario | Expected Behavior | Expected Screen / Status |
| :--- | :--- | :--- | :--- |
| **CHK-02** | **Duplicate Scan:** Scan the exact same ticket from CHK-01 a second time. | 1. Database constraint `check_in_one_active_per_ticket_uidx` triggers unique violation inside savepoint.<br>2. Mobile app flashes **FULL RED SCREEN**.<br>3. Displays warning: *"ALREADY CHECKED IN"*, showing the attendee name and exact timestamp of the first entry. | **HTTP 409 Conflict**<br>`{"error": {"code": "already_checked_in", "checked_in_at": "...", "attendee_name": "..."}}` |
| **CHK-03** | **Wrong Event:** Scan a valid ticket belonging to Event B at Event A's entrance gate. | Ticket is valid in the platform, but belongs to another event. Red screen shows: *"Ticket is for a different event"*. | **HTTP 409 Conflict**<br>`{"error": {"code": "wrong_event"}}` |
| **CHK-04** | **Refunded / Cancelled Ticket:** Scan `TKT_DEMOSEAT00000000F1` (or any ticket refunded via Phase 10). | Ticket status is `refunded`. Red screen shows: *"Ticket is not valid (Refunded or Cancelled)"*. | **HTTP 409 Conflict**<br>`{"error": {"code": "ticket_not_valid"}}` |
| **CHK-05** | **Unknown / Forged QR:** Scan an arbitrary QR code (e.g., `TKT_random_junk_12345`). | Red screen shows: *"Ticket not found"*. | **HTTP 404 Not Found**<br>`{"error": {"code": "unknown_ticket"}}` |

### C. Promotional Code Rejection at the Gate (SRS 4.14)
Per specification, campaign QR codes encoding event links or `CMP_` tokens must **never** be accepted for admission.

| Test ID | Scenario | Expected Behavior | Expected Screen / Status |
| :--- | :--- | :--- | :--- |
| **CHK-06** | Scan bare campaign token: `CMP_STUDENT15ALMATYJAZZ`. | Backend regex catches `CMP_` prefix before ticket lookup. App displays specific error: *"This is a promotional discount code, not an admission ticket."* No check-in record is written. | **HTTP 400 Bad Request**<br>`{"error": {"code": "campaign_token"}}` |
| **CHK-07** | Scan full promotional event URL: `http://localhost:3000/events/jazz?c=CMP_STUDENT15ALMATYJAZZ`. | App/API `ClassifyScannedCode` parses the token out of the URL query and identifies it as a campaign link. Rejected with `campaign_token`. | **HTTP 400 Bad Request** (`campaign_token`) |

## 4. Test Cases: Concurrency & Savepoint Resilience

Verify that concurrent scans at busy venue gates cannot admit two people using duplicated copies of the same QR.

| Test ID | Scenario | Step-by-Step Procedure | Expected Result |
| :--- | :--- | :--- | :--- |
| **CONC-CHK-01** | Simultaneous Scans on 2 Door Devices. | 1. Open Scanner Device A and Device B targeting the same event.<br>2. Aim both devices at the identical paper ticket.<br>3. Trigger scan at the same exact fraction of a second. | • **Device A:** Admits attendee (Green screen, 200 OK).<br>• **Device B:** Blocked by DB unique partial index (Red screen, 409 `already_checked_in`).<br>• Query DB: `SELECT count(*) FROM check_in_records WHERE ticket_id = '...' AND reversed_at IS NULL;` **Must equal exactly 1**. |
| **CONC-CHK-02** | Automated Concurrency Integration Test. | Run: `cd api && go test ./internal/api/ -run TestCheckInIsAtomicUnderConcurrency -v` | Fires 8 parallel goroutines at one ticket. Exactly 1 passes; 7 return 409; exactly 1 active DB record exists. |

## 5. Test Cases: Check-In Reversal (Undo Entry)

* **UI Action:** "Undo Check-in" button on attendee detail modal
* **API Endpoint:** `POST /api/v1/tickets/{id}/check-in/reverse`

### A. Normal Cases (Happy Path)
| Test ID | Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REV-01** | Accidental scan undo: Immediately reverse an accidental check-in. | 1. Check-in record is updated with `reversed_at = now()` (not deleted, preserving audit history).<br>2. Ticket status reverts from `checked_in` to `valid`.<br>3. `tickets.checked_in_at` is cleared to NULL.<br>4. Live event check-in count decrements by 1. | **HTTP 200 OK** |
| **REV-02** | Re-admit reversed ticket: Scan the same ticket again after reversal. | Admission succeeds! A new check-in record is inserted. App displays green screen. | **HTTP 200 OK** (Green screen) |

### B. Error Cases
| Test ID | Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **REV-ERR-01** | Reverse a ticket that was never checked in. | Backend detects no active check-in record. | **409 Conflict** (`ticket_not_checked_in`) |
| **REV-ERR-02** | Reverse without proper authorization (e.g., unassigned user). | Operation blocked by permissions check. | **403 Forbidden** |

## Phase 5 Sign-Off Checklist
You can consider Event Check-In **PASSED** if:
- [ ] Gate staff can only view and scan events they are explicitly assigned to.
- [ ] Revoking gate staff assignment immediately cuts off mobile scanner access (403).
- [ ] Scanning a valid ticket displays a full-screen GREEN confirmation with attendee details.
- [ ] Scanning an already-used ticket displays a full-screen RED warning with first-use timestamp.
- [ ] Multiple scanners hitting the same ticket simultaneously cannot result in double admission (enforced by `check_in_one_active_per_ticket_uidx`).
- [ ] Scanning a campaign QR code (bare token or URL) returns HTTP 400 `campaign_token` and is strictly rejected at the gate.
- [ ] Accidental check-ins can be reversed, restoring the ticket to valid and decrementing gate counts.
- [ ] Manual attendee search allows admission by name/ticket ID without exposing `qr_token` secrets in the API response.
