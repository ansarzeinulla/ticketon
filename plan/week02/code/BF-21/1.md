# Phase 1: Accounts & Authentication Testing Specification

This specification covers **only** Identity, Authentication, and Account Lifecycle (SRS 4.1): registration, sign-in, the session, password reset and email confirmation.

---

## 1. Setup & Environment for the Tester

Before running any test in this phase, start the database, the API (which prints mock emails to its terminal) and the Next.js frontend.

### Terminal 1: Database
From repository root:
```bash
make up
# Start from an empty database:
make reset
```

### Terminal 2: Go Backend API
```bash
make api-run
```
> **Critical Testing Note:** Keep this terminal visible at all times! There is no mail server yet: verification links and password-reset codes are printed to `stdout` in this terminal window.

### Terminal 3: Web Application
```bash
make web-dev
```
Open your browser at: `http://localhost:3000`

Every API call in this document needs `Content-Type: application/json`. Without it the API answers `400 invalid_json`.

## 2. Test Cases: User Registration

* **UI Route:** `/register`
* **API Endpoint:** `POST /api/v1/auth/register`
* **Payload:** `{"email": "...", "password": "...", "full_name": "..."}`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REG-01** | Fill `email`, `password`, and `full_name` with valid values. | User is created in DB; the JWT is stored in the `biletflow_token` cookie; the user lands on `/` already signed in, without a second login step. | **HTTP 201 Created**<br>`access_token`, `expires_at`, `user` object returned. |
| **REG-02** | Omit `full_name` completely (provide only `email` and `password`). | Backend derives `full_name` from the email local part (e.g., `alibek.k@demo.kz` becomes `"Alibek K"`). Account created successfully. | **HTTP 201 Created**<br>`user.full_name` contains formatted local part. |

### B. Edge Cases
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **REG-03** | Register with mixed-case email (e.g., `Dana.Amirova@Example.KZ`). | Email stored and queried via PostgreSQL `citext`. The user can subsequently log in with all-lowercase or all-uppercase. | **HTTP 201 Created** |
| **REG-04** | A password of exactly 72 ASCII characters. | Accepted: 72 bytes is the most bcrypt reads. | **HTTP 201 Created** |
| **REG-05** | New account's status. | `user.status` is `pending_verification` until the email is confirmed (section 5). | **HTTP 201 Created** |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **REG-ERR-01** | Duplicate email (register the REG-01 address again). | **JSON:** `{"error": {"code": "conflict", "message": "An account with this email address already exists."}}`<br>**UI:** banner *"An account with this email already exists. Try signing in instead."* | **409 Conflict** |
| **REG-ERR-02** | Duplicate email with differing letter case (e.g., `DANA@BILETFLOW.KZ`). | Treated as duplicate due to the `citext` column. | **409 Conflict** (`conflict`) |
| **REG-ERR-03** | Malformed email (e.g., `notanemail`, `@missing.com`, `spaces in@email.com`). | **JSON:** `{"error": {"code": "validation_failed", "fields": {"email": "Email must be a valid address such as name@example.kz."}}}`<br>**UI:** the email input is highlighted with the message. | **422 Unprocessable Entity** |
| **REG-ERR-04** | Password longer than **72 bytes** (73 ASCII characters, or a 40-letter Kazakh password, which is 80 bytes in UTF-8). | **JSON:** `{"error": {"code": "validation_failed", "fields": {"password": "Password must not exceed 72 bytes."}}}`<br>Rejected rather than silently truncated by bcrypt. *Known limitation: the cap is in bytes, so a Cyrillic password hits it at 36 letters.* | **422 Unprocessable Entity** |
| **REG-ERR-05** | Blank / missing password or empty body `{}`. | **JSON:** `{"error": {"code": "validation_failed", "fields": {"password": "Password is required."}}}` | **422 Unprocessable Entity** |

## 3. Test Cases: Sign-In & Session Management

* **UI Route:** `/login`
* **API Endpoint:** `POST /api/v1/auth/login` and `GET /api/v1/auth/me`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **LOG-01** | Correct email and password of the REG-01 account. | Authenticates; sets the `biletflow_token` cookie; redirects to `/`. | **HTTP 200 OK**<br>Body has `access_token`, `expires_at`, `user`. |
| **LOG-02** | Deep link with return param: visit `/dashboard` while signed out. | `middleware.ts` bounces the user to `/login?next=%2Fdashboard`. After signing in the user is sent to `/dashboard` rather than `/`. *(The dashboard page itself arrives next week; the redirect is what is tested here.)* | **HTTP 307 Redirect** |
| **LOG-03** | Visit `/login` while signed in. | Redirected to `/`: there is nothing to sign into. | **HTTP 307 Redirect** |

### B. Edge Cases
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **LOG-04** | Email case insensitivity: enter the address in capitals with the correct password. | Successfully authenticates without requiring matching case. | **HTTP 200 OK** |
| **LOG-05** | Timing: log in with an unregistered email vs. a registered email with the wrong password. | Both requests take comparable time (a dummy bcrypt comparison runs for unknown emails). | Comparable response latency. |
| **LOG-06** | Cookie tampering: alter one character of the `biletflow_token` cookie in DevTools and reload. | `middleware.ts` lets the request through (it only sees that a cookie exists), `AuthProvider` calls `GET /auth/me`, gets 401 and clears the corrupt cookie. | **HTTP 401 Unauthorized** |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **LOG-ERR-01** | Wrong password for existing user. | **JSON:** `{"error": {"code": "invalid_credentials", "message": "Email or password is incorrect."}}`<br>**UI:** banner *"Email or password is incorrect."* Does not say which part was wrong. | **401 Unauthorized** |
| **LOG-ERR-02** | Non-existent email. | Identical to `LOG-ERR-01`, so the form cannot be used to find out who has an account. | **401 Unauthorized** |
| **LOG-ERR-03** | Suspended account: `UPDATE users SET status = 'suspended' WHERE email = '...'`, then sign in. | **JSON:** `{"error": {"code": "forbidden", "message": "This account is not allowed to sign in."}}` | **403 Forbidden** |
| **LOG-ERR-04** | Token issued before the suspension: sign in, suspend the account in the DB, then call `GET /auth/me` with the old token. | The API re-reads the account on every authorised request, so the token stops working immediately. | **403 Forbidden** or **401 Unauthorized** |
| **LOG-ERR-05** | `GET /auth/me` with no `Authorization` header. | `{"error": {"code": "unauthorized", ...}}` | **401 Unauthorized** |

## 4. Test Cases: Password Reset Flow

* **UI Routes:** `/forgot-password`, `/reset-password?token=...`
* **API Endpoints:**
  * `POST /api/v1/auth/password-reset/request`
  * `POST /api/v1/auth/password-reset`

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **RST-01** | Submit a registered email on `/forgot-password`. | 1. The page shows a generic confirmation.<br>2. The API terminal prints a `MOCK EMAIL` block of type `account.password_reset` with a code and a link.<br>3. Open the link (`/reset-password?token=...`).<br>4. Enter a new password twice and submit.<br>5. The old password no longer works; the new one does. | **HTTP 202 Accepted** on request.<br>**HTTP 200 OK** on reset. |

### B. Edge Cases & Security Checks
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **RST-02** | Enumeration: submit `doesnotexist@nowhere.kz` on `/forgot-password`. | The response is **identical** to `RST-01`. No email is printed, but the page shows the same confirmation. | **HTTP 202 Accepted** |
| **RST-03** | Superseding tokens: request a reset 3 times in a row for the same address. | The terminal prints 3 codes. Only the **3rd** works; the first two were invalidated. | Codes 1 and 2 fail; code 3 succeeds. |
| **RST-04** | Reset does not sign in. | The response carries no JWT. The page offers *"Go to sign in"*. | No session. |
| **RST-05** | Token hashing: look at `user_tokens` in PostgreSQL. | The plaintext code from the email does not appear. Only its SHA-256 hash is stored. | Plaintext absent from DB. |

### C. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **RST-ERR-01** | Re-use an already consumed code. | **JSON:** `{"error": {"code": "token_invalid", "message": "This reset code is invalid, expired or has already been used."}}`<br>**UI:** *"That code is invalid, expired or already used. Ask for a new one."* | **400 Bad Request** |
| **RST-ERR-02** | Bogus code (e.g., `/reset-password?token=fake12345`). | Same as `RST-ERR-01`. | **400 Bad Request** |
| **RST-ERR-03** | Expired code: `UPDATE user_tokens SET expires_at = now() - interval '1 hour' WHERE ...`, then submit. | Same as `RST-ERR-01`. | **400 Bad Request** |
| **RST-ERR-04** | Different passwords in the two fields on `/reset-password`. | Blocked in the browser: *"The two passwords do not match."* Nothing is sent. | Blocked in UI. |

## 5. Test Cases: Email Verification Flow

* **UI Route:** `/verify-email?token=...`
* **API Endpoints:**
  * `POST /api/v1/auth/verify-email/request` (Bearer)
  * `POST /api/v1/auth/verify-email` (public)

### A. Normal Cases (Happy Path)
| Test ID | Input / Scenario | Expected Behavior | Expected Response / Status |
| :--- | :--- | :--- | :--- |
| **VRF-01** | Request a confirmation for a new account: `curl -X POST localhost:8080/api/v1/auth/verify-email/request -H "Authorization: Bearer <access_token>"`. | 1. The terminal prints a `MOCK EMAIL` of type `account.email_verification`.<br>2. Open the link `/verify-email?token=<TOKEN>`.<br>3. The page submits the code on arrival.<br>4. `users.email_verified_at` is set and `status` becomes `active`.<br>5. A success banner is shown. | **HTTP 202 Accepted**, then **HTTP 200 OK** |

### B. Error Cases & What Errors Must Appear
| Test ID | Input / Scenario | Expected Error Code / Message | HTTP Status |
| :--- | :--- | :--- | :--- |
| **VRF-ERR-01** | Open the confirmation link twice. | The first attempt succeeds. The second: *"That confirmation code is invalid, expired or already used."* | **400 Bad Request** (`token_invalid`) |
| **VRF-ERR-02** | Expired link (move `expires_at` into the past in the DB). | Rejected the same way. | **400 Bad Request** (`token_invalid`) |

## Phase 1 Sign-Off Checklist
You can consider this phase **PASSED** if:
- [ ] Users can register with or without `full_name`.
- [ ] Duplicate emails (including case variants) return HTTP 409.
- [ ] Valid users can log in and the session survives a page reload.
- [ ] Account suspension takes effect on the next request, without waiting for the token to expire.
- [ ] Passwords over 72 bytes are rejected with a 422 instead of being truncated.
- [ ] Resetting a password via the console link works, stores only SHA-256 hashes of the codes, and rejects stale or consumed codes.
- [ ] "Forgot password" does not reveal whether an email has an account.
