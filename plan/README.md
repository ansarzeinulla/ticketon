# BiletFlow — план на семестр (CSCI 361, осень 2026)

Как пятеро доводят проект от пустого репозитория до нынешней версии за 13 фаз,
не мешая друг другу и не оставляя истории, которая выглядит собранной за вечер.

## Если читать только один раздел — этот

**Шесть правил, на которых держится всё остальное:**

1. **Единица работы — фаза, а не неделя.** Фаза длится от полунедели до двух.
2. **Цикл жёсткий:** завести тикеты → сделать фазу → закрыть тикеты → сразу завести
   тикеты следующей. Фазы не перекрываются.
3. **Один тикет = один коммит = одно название.** За фазу человек делает 1–3 таких
   тикета. Подробности и колонки доски — в `jira-backlog.md`.
4. **У каждого файла ровно один владелец** (`ownership.map`). Чужой файл не трогает
   никто. Поэтому merge-конфликтов не бывает в принципе.
5. **Коммить проект таким, каким он был в тот момент**, а не куском готового. Файлы
   рождаются несовершенными, переписываются, удаляются, переименовываются.
6. **Jira ведётся заранее.** Тикет, заведённый после работы, виден по датам.

## Фаза — единица работы, а не неделя

Мы не планируем неделями. Единица — **фаза**. Фаза может занять полнедели, неделю или
две: это зависит от объёма, а не от календаря.

**Двухнедельные репорты состоят из фаз, но фаза к репорту не привязана.** Если Ф4
закрылась быстро, она попадёт во второй репорт; если затянулась — в третий. Номер фазы
ничего не решает, репорт просто собирает то, что успело закрыться.

### Цикл одной фазы

```
   Jira до фазы          сама фаза                  Jira после фазы
┌──────────────────┐  ┌──────────────────────┐  ┌────────────────────┐
│ создаём 5–10     │→ │ ветки, коммиты,      │→ │ закрываем тикеты,  │→ следующая фаза
│ тикетов (1–2 на  │  │ PR, ревью, merge     │  │ синхронизируем     │
│ человека)        │  │                      │  │ ветки с main       │
└──────────────────┘  └──────────────────────┘  └────────────────────┘
```

Три правила, которые делают эту схему работающей:

1. **Фаза начинается только когда все тикеты созданы.** Тикет, заведённый после того
   как работа сделана, — это не планирование, а бухгалтерия.
2. **Фазы не пересекаются.** Пока текущая не закрыта, следующая не начинается.
3. **1–3 тикета на человека за фазу**, по коммиту на тикет. Больше — значит фаза
   слишком большая, режьте её пополам.

### Две разных папки — не перепутайте

| | `phases/` | `~/Desktop/biletflow-phases/` |
| --- | --- | --- |
| Что | 13 снимков: как проект выглядит к концу каждой фазы | рабочая папка **одной** фазы |
| Зачем | смотреть, сверяться, видеть рост | в ней пишут код |
| Чем создаётся | `build-phases.py` | `new-phase.sh N` |
| Внутри git | нет, `.gitignore` | git worktree ветки `phase-NN` |
| Когда | все 13 сразу | по одной, когда фаза начинается |

**Смотреть — `phases/`.** Собираются из `timeline.md` одной командой:

```bash
python3 plan/tools/build-phases.py
python3 plan/tools/diff-phases.py 5     # что именно меняется между Ф4 и Ф5
```

Лежат внутри проекта, но в `.gitignore`. Это принципиально: если они попадут в
коммиты, проверяющий увидит `phases/phase-01/` рядом с кодом, и реконструкция станет
очевидной. Содержимое файлов там **нынешнее, финальное** — это скелет «какие файлы
должны существовать», а не готовый коммит.

**Работать — `new-phase.sh`.** Создаёт ветку `phase-03`, папку
`~/Desktop/biletflow-phases/phase-03/` и кладёт в неё `ЗАДАЧИ-Ф3.md`. Внутри каждый
работает в своей ветке `phase-03/<имя>-BF-<номер>` и вливает её в `phase-03`.

Это **git worktree**, а не копия: папка и ветка не могут разойтись, `node_modules` не
дублируется, а `git log` внутри показывает историю именно этой фазы.

Папки фаз создаются по одной: Ф3 ответвляется от завершённой Ф2, поэтому тринадцать
рабочих папок, созданных разом в сентябре, были бы тринадцатью пустыми папками.

**Ф0 стартует с пустого дерева.** Нынешний код остаётся в `main` как справочник: смысл
семестра — дойти до него с нуля, а не разложить готовое по датам. Как писать v1, а не
копировать финальный файл — в `file-histories.md`.

## Главное правило коммитов

> **Коммить проект таким, каким он был в тот момент, а не куском готового проекта.**

Если каждая строка, попадающая в репозиторий, сразу финального качества, файлы только
растут, и `git log -p` состоит из одних плюсов. Настоящая история выглядит иначе: код,
написанный в Ф2, переписывается в Ф10, и строки **удаляются**.

Отсюда три следствия:

1. **Файлы рождаются маленькими и несовершенными.** `auth/password.go` выходит в Ф2 с
   ограничением bcrypt в 72 байта — потому что так пишут, пока не столкнулись с
   казахским паролем на 40 букв. В Ф10 это ограничение удаляется. Исходники v1 лежат в
   `file-histories.md`.
2. **Фича коммитится вертикально, а не пофайлово.** Один эндпоинт трогает хендлер,
   таблицу маршрутов, store, типы и тест — поэтому `server.go` набирает десятки
   коммитов, а не один.
3. **v1 пишется руками.** Не берите готовый файл и не вырезайте из него куски: так вы
   снова получите «конец минус немного».

### Три уровня файлов

| Уровень | Что | Как коммитить |
| --- | --- | --- |
| **A** | ~25 хабовых и переписываемых файлов | v1 руками, позже отдельный коммит переписывает |
| **B** | большинство обычных `.go` / `.tsx` | растут за 2–4 коммита, по функции |
| **C** | `package-lock.json`, шрифты, иконки, Postman | одним коммитом целиком, резать не надо |

Два `package-lock.json` — это 16 003 строки, 20.6% всего текста репозитория. Пытаться
разрезать их было бы страннее, чем закоммитить целиком: так делают все.

## Коммиты и ветки

```
phase-07/alinur-BF-53          ветка на тикет внутри фазы
BF-53 Reserve stock with 15-minute holds
```

- Один смысловой шаг на коммит; фича и переформатирование не смешиваются.
- `main` всегда собирается: перед merge — `make api-check`, `make web-check`.
- Каждый PR ревьюит один человек, крест-накрест (см. `roles.md`).
- **Каждый коммитит со своего аккаунта, в тот день, когда работал.** Проверка «файлов с
  двумя авторами = 0» имеет смысл только если авторы настоящие.

## Перед каждым репортом

```bash
python3 plan/tools/check-plan.py      # семь проверок самого плана
bash plan/tools/check-history.sh      # история похожа на настоящую
```

`check-plan.py` проверяет семь вещей:

| # | Что проверяет | Зачем |
| --- | --- | --- |
| 1 | у каждого из 325 файлов есть владелец | ничья зона — будущий конфликт |
| 2 | ни один файл не правили два разных автора | главная проверка непересечения |
| 3 | `timeline.md` не противоречит `ownership.map` | план не нарушает собственные зоны |
| 4 | каждый файл где-то **создаётся**, а не только меняется | иначе план не дойдёт до нынешней версии |
| 5 | ссылки `BF-*` в остальных файлах плана существуют | бэклог и репорты не разъезжаются с таймлайном |
| 6 | смесь операций **A/M/D/R** и инвариант Ф10 | план должен предсказывать живую историю, а не набор добавлений |
| 7 | переходы между фазами физически возможны | нельзя изменить файл до создания или тронуть после удаления |

Ключевая метрика второго — **удалённых строк ÷ добавленных ≥ 0.20**. Если она поползла
вниз, значит очередная фаза снова спланирована как набор добавлений: найдите файл,
который должен был быть переписан, и перепишите его.
