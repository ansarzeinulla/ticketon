# Phase 3: Attendee Checkout & Inventory Testing Specification

This specification covers **only** the attendee side: the public catalogue and event page, ticket selection, prices in KZT, the simulated checkout, inventory locking, assigned seats, the paid-sales gate and order placement (SRS 4.3, 4.3.1, 4.4, 4.5, 4.6).

---

## 1. Setup & Environment for the Tester

Treat this as an independent testing phase. Checkout must work completely without being logged in (guest mode), but can also be tested with a logged-in user.

### Terminal 1: Database
```bash
make up
make seed
```

### Terminal 2: Go Backend API
```bash
make api-run
```

### Terminal 3: Web Application
```bash
make web-dev
```

### Test Target
Open a private/incognito browser window at:
`http://localhost:3000/events` - the catalogue - or directly
`http://localhost:3000/events/almaty-winter-jazz-night`.

## 5. Test Cases: Concurrency & Overselling Prevention

PostgreSQL row locking (`SELECT … FOR UPDATE`) and `ticket_types_inventory_chk` stop two attendees buying the same last ticket.

| Test ID | Scenario | Step-by-Step Test Procedure | Expected Result |
| :--- | :--- | :--- | :--- |
| **CONC-01** | **Two buyers, one ticket** | 1. Set a tier to `quantity_total = 1`.<br>2. Open the event page in two browsers.<br>3. Select the ticket and open checkout in both.<br>4. Pay in Browser A, then within a second in Browser B. | • **A:** goes to `/orders/[id]`.<br>• **B:** **HTTP 409** `{"error": {"code": "insufficient_inventory", "remaining": 0}}` and the banner *"These tickets sold out while you were choosing. The page has been refreshed."* |
| **CONC-02** | Automated race | `cd api && go test ./internal/api/ -run TestCheckoutDoesNotOversellUnderConcurrency -v` | 30 buyers, 10 tickets: exactly 10 succeed, 20 get 409, `quantity_sold` is exactly 10. |
| **CONC-03** | Over real HTTP | With the API running: `make api-smoke`. | Checks 11-12c: after a sale `quantity_sold` is right, a basket bigger than what is left is refused with `insufficient_inventory`, and nothing is written. CI runs this on every pull request. |

## 10. Test Cases: Reservations and the Processing Charge (SRS 4.6)

Choosing seats reserves them for 15 minutes; paying confirms the reservation.
Stock that is reserved is not sold, and cannot be sold to anyone else meanwhile.
A general-admission checkout goes through the same reservation on the server,
created and confirmed in one request.

* **API Endpoints:** `POST /api/v1/events/{id}/holds`, `GET` / `DELETE /api/v1/orders/{id}/hold`, `POST /api/v1/orders/{id}/confirm`
* **Event:** any assigned-seating event (section 7)

| Test ID | Scenario | Expected Behavior | Expected Result |
| :--- | :--- | :--- | :--- |
| **HOLD-01** | Pick two seats and click "Hold these seats". | *"Your seats are held"* with a 15-minute countdown, the seats' price, the processing charge on its own line and the total. In another browser the two seats show as held (⏳). | **HTTP 201**, order `pending` |
| **HOLD-02** | Pay within the 15 minutes. | The reservation turns into a sale: the seats become sold, tickets are issued. | **HTTP 200**, order `paid` |
| **HOLD-03** | Let the countdown run out, then pay. | *"Your reservation ran out"*; the seats are back on sale and the map is shown again. | **HTTP 409** `hold_expired` |
| **HOLD-04** | Click "Release the seats". | The seats are back on sale at once, not after 15 minutes. | `DELETE …/hold` **200** |
| **HOLD-05** | With the map already open in a second browser, hold one of the seats the first browser holds. | Refused; the map is re-read and shows the seat as held. | **HTTP 409** `seat_taken` |
| **FEE-01** | Set `PROCESSING_FEE_PERCENT=5` in `.env`, restart the API, hold 1 seat. | The quote and the order both carry a processing charge of 5% of the seat's price (`350.00` on a 7 000 KZT seat). | Fee follows the configuration |

## Phase 3 Sign-Off Checklist
You can consider Attendee Checkout **PASSED** if:
- [ ] Attendees can check out as guests without an account.
- [ ] Free checkouts create an order and tickets with no payment step.
- [ ] Paid checkouts record a simulated payment, move inventory and issue tickets in one transaction.
- [ ] Overselling is impossible under concurrency (409 `insufficient_inventory`, automated race test, `make api-smoke`).
- [ ] Paid tiers are refused until activation is complete; free tiers are not.
- [ ] A seat can be sold once, at the price of its section.
- [ ] Totals are exact KZT, never float-rounded, and include the 3.5% processing charge on paid orders only.
- [ ] Choosing seats reserves them for 15 minutes; an expired or released reservation puts them back on sale.
- [ ] Cancelled and unpublished events refuse checkout.
- [ ] The organizer sees each order and each ticket holder.
