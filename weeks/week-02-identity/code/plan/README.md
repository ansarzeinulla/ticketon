# BiletFlow — план на семестр (CSCI 361, осень 2026)

Как пятеро доводят проект от пустого репозитория до работающей системы за 10 недель,
не мешая друг другу.

## Где ваши инструкции

**Не здесь.** Этот файл читают один раз. Каждый день вы открываете свой файл в
папке недели:

```
weeks/week-05-gate/
    captain.md    ← капитану: открыть неделю, следить, закрыть, поставить тег
    S1.md … S5.md ← каждому своё: ветка, файлы, команды, что двигать в Jira
    code/         ← как проект выглядит к концу этой недели
```

Внутри готовые команды — копируются и выполняются, думать не надо. Собираются
командой:

```bash
python3 plan/tools/build-weeks.py
```

## Шесть правил

1. **Единица работы — календарная неделя**, понедельник–воскресенье. W1 начинается
   14 сентября.
2. **Цикл жёсткий:** капитан заводит задачи → неделя работы → капитан закрывает
   задачи → сразу заводит задачи следующей. Недели не перекрываются.
3. **Одна задача = один коммит = одно название.** За неделю человек делает 1–3
   такие задачи.
4. **У каждого файла ровно один владелец** (`ownership.map`). Чужой файл не
   трогает никто — поэтому merge-конфликтов не бывает в принципе.
5. **Коммитим то, что написано сегодня**, а не то, как оно будет выглядеть в конце.
   Файлы рождаются простыми, переписываются, удаляются, переименовываются.
6. **Jira ведётся заранее.** Задача, заведённая после работы, видна по датам.

## Кто за что отвечает

| | Зона |
| --- | --- |
| **S1** | бэкенд-ядро, БД, интеграция · **капитан** |
| **S2** | бэкенд коммерции: события, билеты, checkout, возвраты |
| **S3** | веб для зрителя, типы и клиент API, локализация |
| **S4** | веб организатора и админа, аналитика, поддержка |
| **S5** | мобильное приложение, QA, DevOps |

**Все PR смотрит и вливает капитан.** Друг друга не ревьюим: одно место принятия
решений — меньше путаницы и не бывает «а я думал, ты посмотришь». Капитан свои PR
вливает сам, но только с зелёным CI.

Точное распределение всех файлов — в `ownership.map`. Это единственный источник
правды; спорить о том, чей файл, не нужно — посмотрите в карту.

W1–W8 — разработка, W9–W10 — хвост. Каждая неделя идёт по одному шаблону:

```
вс разбор  →  пн–пт код  →  сб ревью  →  вс слияние и закрытие
```

Репорты собирают то, что успело закрыться. Если неделя переехала в соседний
репорт — это нормально, переписывать ничего не надо.

## Три ветки

| Ветка | Живёт | Кто трогает |
| --- | --- | --- |
| `main` | всегда | **никто напрямую** |
| `week-05` | одну неделю | все пятеро вливают в неё свои PR |
| `week-05-alibi-BF-40` | одну задачу | один человек, один коммит |

Имя ветки задачи — **через дефис**, а не через слэш: пока существует ветка
`week-05`, git отказывается создавать `week-05/что-угодно`.

Ветки задач удаляются сами после слияния (галочка *Automatically delete head
branches*). Ветки недель остаются навсегда — по ним видно, как рос проект.

## Главное правило коммитов

> **Коммитим то, что написано сегодня, а не то, как оно будет выглядеть в конце.**

Если гнаться за финальным качеством каждой строки, файлы только растут, а `git log -p`
состоит из одних плюсов. Нормальная разработка выглядит иначе: код, написанный в W2,
переписывается в W8, и строки **удаляются**.

Поэтому не бойтесь писать просто и переделывать потом. `auth/password.go` выходит в
W2 с ограничением bcrypt в 72 байта — потому что так пишут, пока не столкнулись с
казахским паролем на 40 букв. В W8 это ограничение удаляется. Исходники первых
версий лежат в `file-histories.md`: когда в вашей инструкции стоит пометка
**v1**, берите оттуда.

Три уровня файлов:

| Уровень | Что | Как коммитить |
| --- | --- | --- |
| **A** | ~25 хабовых и переписываемых файлов | v1 руками, позже отдельный коммит переписывает |
| **B** | большинство обычных `.go` / `.tsx` | растут за 2–4 коммита |
| **C** | `package-lock.json`, шрифты, иконки, Postman | одним коммитом целиком |

## Файлы этой папки

| Файл | Что это |
| --- | --- |
| `README.md` | этот файл: правила, роли, календарь |
| `frozen.txt` | номера закрытых недель — генераторы их не переписывают |
| `students.md` | кто есть кто: имена, ID, аккаунты GitHub, зоны |
| `ownership.map` | **источник правды:** правила «файл → владелец» |
| `reports/` | семь двухнедельных отчётов |

Понедельные инструкции в `weeks/` и отчёты **генерируются** из `timeline.md`.
Руками их не правят: правят таймлайн и перезапускают генератор. Таймлайн,
`file-histories.md` и `tools/` — локальная оснастка команды, в репозиторий они
не коммитятся (см. `.gitignore`).

| Инструмент | Что делает |
| --- | --- |
| `tools/build-weeks.py` | пересобирает `weeks/`: снимки кода + все инструкции |
| `tools/gen-reports.py` | пересобирает семь отчётов |
| `tools/check-plan.py` | семь проверок самого плана |
| `tools/stats.py` | сколько кому предстоит сделать: файлы и строки по неделям |
| `tools/diff-weeks.py N` | что меняется между W(N−1) и WN |
| `tools/new-week.sh N` | ветка `week-NN` + рабочая папка |
| `tools/check-history.sh` | метрики истории: доля правок, удалений, переименований |

## Перед каждым репортом

```bash
python3 plan/tools/check-plan.py      # семь проверок плана
bash plan/tools/check-history.sh      # метрики истории
```

`check-plan.py` проверяет:

| # | Что проверяет | Зачем |
| --- | --- | --- |
| 1 | у каждого файла есть владелец | ничья зона — будущий конфликт |
| 2 | ни один файл не правили два автора | главная проверка непересечения |
| 3 | `timeline.md` не противоречит карте | план не нарушает собственные зоны |
| 4 | каждый файл где-то **создаётся** | иначе в плане дыра: файл есть, а взяться ему неоткуда |
| 5 | ссылки `BF-*` существуют | документы не разъезжаются с планом |
| 6 | смесь операций A/M/D/R | план должен предсказывать живую историю |
| 7 | переходы между неделями возможны | нельзя изменить файл до создания |

Ключевая метрика второго скрипта — **удалённых строк ÷ добавленных ≥ 0.20**.
Поползла вниз — значит неделя спланирована как набор добавлений: найдите файл,
который должен был быть переписан, и перепишите его.
