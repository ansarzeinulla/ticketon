# Phase 8: Support Chat & Case Management Testing Specification

This specification covers **only** attendee contextual support requests, organizer support inboxes, asynchronous message threads, internal staff notes, case lifecycle statuses, polling intervals, and permission isolation (SRS 4.13, UC9, Phase 8, and Phase 10).

## 4. Test Cases: Polling Intervals (SRS 4.13 Sockets-Free Rule)

Per specification, the academic MVP deliberately avoids WebSockets in favor of lightweight REST polling.

| Test ID | Scenario | Verification Method | Expected Behavior |
| :--- | :--- | :--- | :--- |
| **POLL-01** | **Active Thread Polling:** Keep open thread visible in Browser A. In Browser B, send a reply. Do not refresh Browser A. | Watch Browser A Network tab in DevTools. | Browser A polls `GET /support/cases/{id}` approximately every **10 seconds**. The new message renders automatically within 10s. |
| **POLL-02** | **Organizer Inbox Polling:** Keep Organizer Inbox open on `/dashboard/events/[id]`. Attendee opens a new case in Browser A. | Watch Organizer Network tab in DevTools. | Organizer inbox polls `GET /events/{id}/support/cases` approximately every **15 seconds**. New case appears without page reload. |
| **POLL-03** | **Resolved Thread Halts Polling:** Move case status to `Resolved`. | Keep resolved thread open. Watch Network tab for 60 seconds. | **Zero polling requests occur.** The client stops polling to avoid querying finished conversations indefinitely. |

## 7. Test Cases: Security, Privacy & The 404 Anti-Leak Rule

Per SRS 4.13, unauthorized users must not be able to view cases they are not party to. Crucially, unauthorized requests must return **404 Not Found, not 403 Forbidden**, so that the existence of a support request is not leaked.

| Test ID | Scenario | Request Made | Expected Status & Result |
| :--- | :--- | :--- | :--- |
| **SEC-SUP-01** | **Cross-User Privacy (The 404 Rule):** User C (`nurlan@example.kz`) attempts to view User A's (`aigerim@...`) support thread. | Authenticated `GET /api/v1/support/cases/<CASE_A_UUID>` with User C's token. | **HTTP 404 Not Found**<br>`{"error": {"code": "not_found"}}`<br>*(Returns 404 instead of 403 to prevent confirming the case exists).* |
| **SEC-SUP-02** | **Cross-Organizer Privacy:** Organizer B (`timur@...`) attempts to view a support case belonging to Organizer A's event. | Authenticated `GET /api/v1/support/cases/<CASE_A_UUID>` with Organizer B's token. | **HTTP 404 Not Found** (`not_found`) |
| **SEC-SUP-03** | **Platform Admin Access:** Platform Admin (`support@biletflow.kz`) views User A's support thread. | Authenticated `GET /api/v1/support/cases/<CASE_A_UUID>` with Admin token. | **HTTP 200 OK**<br>Admins have global support visibility for moderation. |
| **SEC-SUP-04** | Unauthenticated Access: Query `/support/cases/{id}` without bearer token. | Unauthenticated request. | **HTTP 401 Unauthorized** |

## Phase 8 Sign-Off Checklist
You can consider Support Chat & Case Management **PASSED** if:
- [ ] Attendees can choose from the standardized categories to open cases linked to their orders.
- [ ] Guest buyers are cleanly guided to sign in or register with their checkout email to access support.
- [ ] Contextual metadata (`order_id`, `event_id`, `user_id`) is automatically bound to the case.
- [ ] An organizer's first public reply automatically transitions status to `in_progress` and assigns the case.
- [ ] Client polling operates at ~10s for active threads, ~15s for the organizer inbox, and stops completely upon case resolution.
- [ ] Staff internal notes are completely excluded from attendee view (both in the UI and raw API response).
- [ ] Reopening a resolved case properly clears `resolved_at` in PostgreSQL.
- [ ] Unauthorized users attempting to view another user's case receive HTTP 404 (not 403), preventing case existence leakage.
- [ ] Public messages generate formatted `support.new_message` console logs, while internal notes generate no attendee emails.
